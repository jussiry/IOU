Overview & vision

A standalone HTML/JS app that analyses a codebase and renders it as an interactive dependency graph. Each file is a node; each import/require relationship is an edge. The goal is to make the shape of a codebase legible at a glance: what depends on what, which files are hubs, and what a given file actually does.

Currently lives inside the IOU repo for convenience, but is designed to be extracted into its own repository. It has its own package.json and no dependency on IOU's code.

Who it's for

This tool is aimed at codebases written mostly by AI, to give humans easier access into them. The file's leading description comment — authored by the AI — is the human-readable handle on each file, and the dependency graph is how you navigate between them.

  • Now (v1) Read-only. Analyse a codebase, render description comments as nodes, browse by dependency.
  • Later An iterative human↔AI loop: AI writes a file's description comment → the user edits the comment as an instruction for change → AI modifies the code accordingly → AI rewrites the description comment to match. The graph becomes the editing surface for this loop.

This is why nodes are (destined to be) editable DOM and why category/metadata lives in the comment: the comment is the contract between human and AI.

What's novel here

No tool found combines all three:

  1. Nodes whose body is the human-written leading description comment — the author's prose as first-class node content, not just extracted structure.
  2. Editable nodes / future in-node HTML editor — prior art is almost all read-only viewers. The graph as an editing workspace is the differentiator.
  3. Overview (loose graph) ↔ Focus (neighbourhood of rich cards) as the primary navigation — like Sourcetrail but at file granularity with rich editable cards.

What's built

Everything on this page exists and works in the app today. It documents the current, shipped behaviour — the forward-looking design lives under Roadmap and Zoom modes.

The node graph

  • Overview layout — the whole graph renders as minimal name-only pills, coloured and iconed by category, positioned by a d3-force simulation with a custom box-collision force (see Architecture).
  • File purpose on hover — hovering a node shows a floating, screen-space description card built from the file's leading description comment, rendered as lightweight markdown (ui/markdownish.js). The card is placed by an outward search that avoids covering highlighted neighbours, then clamped to the viewport. Leaving a node keeps the card alive for a short grace period so the pointer can travel onto it.
  • Dependency highlight — hovering rings the node and its 1-hop neighbours and colours the connecting edges by direction: blue = depends-on (outgoing), orange = depended-on-by (incoming). Everything unrelated dims.
  • Card badges — the hover card shows the file extension, exported-function count (ƒ), exported-constant count (#), and file size (K for ≥1000 chars).
  • Symbol views — the ƒ and # badges are toggle buttons. ƒ swaps the description for a read-only CodeMirror 6 editor listing the module's exported functions (signatures, bodies folded to one line); # lists the exported constants (one-line values inline, multi-line folded). The analyser (analyser/exports.js) captures each export's source; the editor (ui/symbol-editor.js) folds multi-line entries on load. Read-only for now.
  • Draggable nodes + pan/zoom — drag a node to pin it where dropped (this gently reheats the simulation so neighbours rearrange); drag the background to pan; wheel to zoom. Both layers share one d3-zoom transform.

Encoding & layout

  • Category → colour + symbol — read verbatim from each file's @category tag; unknown/missing falls back to neutral grey. See Categories & colours.
  • Size encodes file size — node size scales with character count (sqrt-scaled), so big modules stand out; bigger nodes also carry stronger charge repulsion, pushing neighbours further away.
  • Vertical hierarchy — the layout stacks the codebase by dependency depth: consumers / entry points float to the top, foundational modules sink to the bottom. Each node's level is a longest-path layering of the dependency DAG (graph/hierarchy.js, cycle-safe via back-edge skipping); a forceY nudges nodes toward their level. Tune LAYER_GAP (default 130) and HIERARCHY_STRENGTH (default 0.22) in graph/simulation.js — 0 disables it.

Filtering the view

  • Size filter — a top-bar segmented control (All / Medium & large / Large only) hides smaller files and any edges touching them. Tiers come from char count (small <3000 ≤ medium <8000 ≤ large); positions are kept (no relayout).
  • Category toggles — the legend swatches double as on/off buttons: click a category to hide all its nodes; click again to restore. A "toggle all" control flips every category at once. When the legend doesn't fit the header it collapses into a "Categories" dropdown. Size filter and category toggles share one visibility pass (graph/filters.js).

Not yet Text search is not implemented — only the size and category filters above exist.

Core requirements

The original design constraints, each tagged with its current state.

  1. Automatic layout is the priority. With potentially hundreds of varying-size, varying-degree nodes, the initial arrangement is computed by a force-directed layout. Connectedness drives proximity; clusters emerge naturally.
  2. Varying node sizes. Node dimensions depend on content and importance, so the layout avoids overlaps between unequal boxes (the custom AABB collision force).
  3. Draggable nodes. Users can nudge nodes; the layout is a starting point, not a cage.
  4. Visually editable nodes. Colours and symbols convey file kind today, but node content is not yet editable — that (and the eventual in-node HTML editor) is planned.
  5. Semantic zoom (level-of-detail). Content should adapt to zoom level — minimal zoomed out, richer zoomed in. Not yet active; see Zoom modes.
  6. Scale. Must stay usable for a whole codebase (hundreds of files, thousands of edges). The current 74-file / 231-edge graph settles instantly; scaling knobs are noted under Zoom modes.

Rendering model

Edges are SVG lines/arrows in a back layer; nodes are absolutely-positioned HTML <div>s in a front layer. Both layers share the d3-zoom transform so they pan/zoom together while node content stays editable DOM.

Pipeline

  1. Scan — discover source files (configurable root + glob).
  2. Analyse — per file, extract (a) dependency edges from import/require, resolving to in-project files (handling the .js-import → .ts-file case and index.* directories), and (b) the leading description comment including any @category tag (read verbatim, not inferred), plus exported symbols.
  3. Build — produce nodes and edges per the schema, attaching size tiers/scales.
  4. Layout — run the d3-force simulation; connected files cluster; the box-collision force keeps varying-size boxes apart.
  5. Render — HTML node pills styled by category; edges in the back layer.
  6. Interact — drag to rearrange; hover to highlight the 1-hop neighbourhood; filter by size/category.

Design decisions

Library: D3 (modular) with HTML-div nodes

The deciding factors are editable HTML node content, easy content swapping, and semantic zoom — all of which favour nodes that are real DOM elements rather than canvas-rendered overlays.

  • Nodes are live DOM. Each node is an absolutely-positioned <div> synced to the zoom transform. Content is plain HTML we own, so "change content easily" and a future in-node editor are natural. (Cytoscape renders to canvas and can only overlay HTML — awkward for in-node editing.)
  • Connection-driven auto-layout via d3-force: forceLink (springs), forceManyBody (repulsion), forceCenter.
  • Modular — import only d3-selection, d3-force, d3-zoom, d3-drag (~50–70 KB); never the full ~270 KB bundle.
  • Zero framework, full control over rendering and interaction.

Overlap removal — nodes are boxes, not circles

D3's built-in forceCollide is circle-based and would reserve a circle big enough to hold each rectangular card, leaving wasteful gaps around wide/tall nodes. Instead we use a custom rectangular (AABB) collision force: each node is a width × height box, and overlapping boxes are pushed apart along their minimum-overlap axis. This packs tightly, is ~30 lines, and is the standard approach when node shape matters.

Compound nodes / grouping

D3 has no built-in compound-node primitive. Planned approaches when grouping is needed: hierarchical (d3-hierarchy pack/treemap for true nesting by folder/module), or force-layout grouping (draw a convex hull around each cluster and add an attraction force).

Other decisions made

  • Analysis runtime. A Node analyser → graph.json step; the UI loads the JSON. Browser folder-picking is a possible later enhancement.
  • Categories come from the comment, not inference. The analyser does not classify files. Each file declares its own @category; the visualiser just maps it to a colour/symbol. No fragile heuristics.
  • Separate graphs are separate. Backend / tests / client app are disjoint dependency graphs and aren't shown together. Which graph (or folder root) to view is a top-level choice.

Zoom modes (overview vs focus)

Two viewing modes, each with its own scope, node visual, and physics. Mode A (Overview) is implemented; Mode B (Focus) and the transition between them are planned.

Mode A — Overview (bird's-eye)

  • Scope: the whole graph — all nodes and edges.
  • Node visual: minimal pill showing the file name only, coloured/iconed by category.
  • Edges: thin lines; direction de-emphasised until hover.
  • Goal: see the structure of the whole codebase at a glance — hubs, clusters, isolated files.

Mode B — Focus (neighbourhood)

  • Scope: the focused node + its 1-hop neighbours only — depends on (outgoing) and depended on by (incoming).
  • Node visual: rich text boxes — title + description + badges. Focused node centred and largest.
  • Edges: directional arrows that clearly separate the two groups.
  • Re-focus: click a neighbour to recentre. Exit: Esc / back returns to Overview, restoring prior pan/zoom.

Transition

A node morphs circle → box entering Focus; content cross-fades from name-only to the full card; non-neighbour nodes fade out. Reverse on exit. Positions animate rather than jump.

Physics & performance note

The original idea was circle physics in Overview, box physics in Focus, on the assumption box physics for hundreds of nodes would lag. It won't — with a quadtree, both run ~O(n log n) and a few hundred nodes settle at 60fps. The real cost at scale is the DOM: hundreds of rich cards repositioned every tick. Therefore:

  • Box physics in both modes (already the case) — physics is not the bottleneck.
  • The Overview/Focus split is justified by DOM cost + legibility: Overview renders little per node; Focus renders rich boxes for only a handful of neighbours.
  • Settle the simulation (alphaMin) and stop ticking when idle; re-run only on interaction.
  • Optimisation knobs, only if Overview feels heavy (in order): render overview nodes as canvas/SVG circles; then switch Overview to the cheaper circle-collision force.

Categories & colours

A file's category is declared inside its leading description comment via a tag the analyser reads verbatim. The mechanism is implemented; the vocabulary below is a first draft to react to. 

/**
 * mesh.js — maintains the WebRTC peer mesh: tracks connected peers,
 * handles reconnection, and routes signalling messages.
 *
 * @category network
 */

The visualiser maps the tag to a colour + symbol. This keeps classification out of the analyser (no fragile heuristics) and in the hands of whoever writes the comment (AI, then user).

Single category now, tags later

v1 uses one category string per file. Category boundaries aren't always clean, so we may move to an ordered tag list where the first tag is primary (→ colour) and secondary tags get a lighter treatment. To keep that shift cheap, the colour lookup already accepts either category or a tags[] array (first element = primary), so adding tags is additive, not a rewrite.

graph.json schema

The contract between analyser and UI (and the shape of the dummy file). Updated to include the fields the analyser actually emits — the old README schema listed only id/name/path/category/description/loc and omitted chars, exports, and symbols. 

{
  "root": "app",                          // analysed root (relative label)
  "nodes": [
    {
      "id": "app/js/peer/mesh.js",        // unique; repo-relative path
      "name": "mesh",                     // short label (folder name for index.*)
      "path": "app/js/peer/mesh.js",
      "category": "network",              // from @category; may be absent
      "description": "Maintains the WebRTC peer mesh...", // full comment text
      "loc": 240,                         // non-blank lines
      "chars": 6120,                      // file length → size tier + node size
      "exports": { "fns": 4, "consts": 2 },        // counts for the ƒ / # badges
      "symbols": {                                  // full source per symbol
        "fns":    [ { "name": "connect", "code": "export function connect(...) {...}" } ],
        "consts": [ { "name": "MAX_PEERS", "code": "export const MAX_PEERS = 8;" } ]
      }
    }
  ],
  "edges": [
    // source depends on target (source imports target).
    // "depends on" = outgoing; "depended on by" = incoming.
    { "source": "app/js/peer/mesh.js", "target": "app/js/peer/client.js" }
  ]
}

Prior art

Web research, June 2026. The core concept — browsing code by dependency structure rather than the file tree — is proven, but our specific angle (editable, file-level, description-comment nodes) is largely unexplored.

Closest concept match — Sourcetrail

Sourcetrail (FOSS, discontinued 2021). Select a symbol and the graph focuses on it, showing all incoming and outgoing dependencies — essentially our Focus mode, at symbol granularity. It proved the graph-as-navigation model; its abandonment is an opportunity. Study its UX.

Closest pipeline match — CodeAtlas

CodeAtlas (open source). Turns a repo into a self-contained codeatlas.html interactive file dependency graph plus module-map.json + summary.md — almost exactly our "Node analyser → JSON → HTML viewer" pipeline.

Adjacent — read-only viewers / onboarding maps

  • CodeSee — code maps of services/dirs/file deps, upstream+downstream, onboarding focus.
  • GitKraken Codemaps, NDepend (dependency matrix + graph), Emerge (browser-based, multi-language).
  • A shared Claude Code D3.js prompt generates dependency graphs with 3 zoom levels (system / module / full) — independent convergence on our semantic-zoom idea.

Running & analysing

Run the app

Plain static files — no build step, no npm install needed.

npm run dev          # node scripts/serve.mjs 8088 (serves this folder)
# then open:
open http://localhost:8088/

scripts/serve.mjs is a tiny static server that sends Cache-Control: no-store, so edited ES modules always reload (browsers otherwise cache modules and keep running stale code after edits).

Must be served over HTTP — do not open index.html as a file://. ES modules and fetch() are blocked on the file:// origin, which shows a blank page.

Offline / no CDN. d3 is vendored as a single self-contained bundle at vendor/d3.js; the import map maps the bare d3-* specifiers to it. Nothing is fetched at runtime.

Rebuild the CodeMirror bundle

CodeMirror 6 (the hover card's read-only symbol editor) is vendored the same way: vendor/codemirror.js is a single esbuild bundle of scripts/cm-entry.mjs. Bundling from one entry keeps CM's core a singleton (separately-bundled CM packages would duplicate it and break facet/StateField identity). Rebuild after changing the entry or upgrading CM: 

npm run vendor:cm   # esbuild scripts/cm-entry.mjs → vendor/codemirror.js

Analyse a codebase

node src/analyser/cli.js <root> [--out data/graph.json]   # default root: ../app

The analyser walks the root (skipping dist/vendor/node_modules), extracts each file's in-project imports and its leading description comment + @category, and writes data/graph.json (gitignored; the UI loads it, falling back to the committed data/graph.sample.json). Import resolution handles the .js-import → .ts-file case and index.* directories.

scripts/add-categories.mjs <root> is the one-off (idempotent) migration that stamped an @category tag into every app/ source file's leading comment, seeded from a directory→category map. Re-running skips already-tagged files.
