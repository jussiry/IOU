Design roadmap

The plan for this site itself: what Design is, the decisions behind it, and what's built versus still ahead. Kept here so Design documents its own direction.

What it is

One place to understand — and eventually to shape — how Tally works, unifying what is today scattered across TIPs/, specs/, plan/, and GLOSSARY.md into a cross-linked, text-first HTML site. Each page reads cleanly as raw source (for a human or an AI) and renders as a paged, navigable doc site — the GraphEditor readme.html pattern, generalised to a whole multi-document project.

Decisions made

  • Name: Design. Covers system design (what the docs are) and the authoring/tooling future, without a later rename.
  • Many standalone HTML pages at design/*.html, tied together by a shared shell; CSS/JS/manifest tucked under design/assets/.
  • HTML is the source — no Markdown+render step. Chosen for flexibility while the shape of the whole system is still emerging, and to keep the eventual in-browser editor simple (one format).
  • Text-first + progressive enhancement. Content lives in the markup; JS only adds the topbar + sidebar. JS off = a plain readable page.
  • Status convention carried over from GraphEditor: implemented planned proposal reference.
  • Migrate incrementally, don't block on merges. Bring existing docs in as-is, tag their status, cross-link, and reconcile conflicts in place. Hand-written plan/ notes are preserved for their original rationale even where parts have aged.

Phasing

  1. Static site. Build the shell, migrate + reconcile the docs, cross-link, serve at a /design route, point CLAUDE.md at it.
  2. In-browser editor. Edit a page's prose and save. The hard part is persistence: File System Access API for a local author, or an authenticated write endpoint when deployed. The editing UI (contenteditable on the semantic blocks) is the easy part. Deferred.
  3. Absorb GraphEditor under design/graph/, sharing the shell, so a spec page can deep-link to the live dependency graph and back.

Known drift to reconcile

Consolidation surfaces existing inconsistencies — that's a feature. Flagged for when each area becomes canonical here:

  • Two glossaries: root GLOSSARY.md and specs/glossary.md hold different content.
  • plan/idea.md overlaps README.md.
  • Several specs may be stale versus current code; each imported page should get a status and a "verified against code on <date>" line.

Open questions

  • Do specs/plan/TIPs keep their own identities as sections, or dissolve into one flat topic list?
  • When does Design become AI's canonical source, so CLAUDE.md and the scattered docs point into it?
  • Editor persistence model for the deployed case (auth + conflict).
