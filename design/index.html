Design

One place to understand — and, in time, to shape — how Tally works. Overview, architecture, specs, glossary, and design proposals (TIPs), cross-linked and honest about what is built versus merely planned.

"Design" here means system design (how the app is built), not visual design. Everything is authored text-first as plain HTML: each page reads cleanly as raw source for a human or an AI, and with JavaScript off it is just a readable page. The shared sidebar and topbar are progressive enhancement — they add navigation, never content, so the markup of each page stays the single source of truth.

Status convention

Every page — and, where useful, individual claims — carries a status so its maturity is explicit in the source and colour-coded in the render:

  • implemented — exists and works in the code today
  • planned — decided and well-defined, not built yet
  • proposal — a suggestion, draft, or open question
  • reference — background, rationale, or a spec/contract

When a page makes claims about the code, it should say when they were last verified against it (e.g. "verified 2026-07-09"), not assume they stay true forever.

How this is organised

  • Standalone pages. Each topic is its own .html file in design/; the sidebar (from assets/pages.js) ties them together. CSS/JS live under assets/, out of the way.
  • Migrated incrementally. Existing docs (TIPs/, specs/, plan/, GLOSSARY.md) move in over time. They may conflict with each other or with the code at first — that is expected. The plan is to bring them in, tag their status, and reconcile in place rather than block on a perfect merge. The hand-written plan/ notes in particular hold original rationale worth preserving even where parts have aged.
  • Scope. For now this covers the Tally app. GraphEditor (the dependency-graph tool) is a candidate to fold in later, at which point Design spans documenting and editing/visualising.
