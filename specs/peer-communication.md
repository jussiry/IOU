# Peer communication protocol

This document specifies how IOU clients exchange application messages with each other. It is written as a protocol-level spec so the same rules can be implemented on any transport, by any client, and against any compatible relay server.

The core ideas are:

- **Every user is their own identity.** A user is a public key. There is no central user directory; a client only needs the recipient's public key to talk to them.
- **Every message is encrypted end-to-end between a pair of users.** The relay server learns routing metadata (sender, recipient, message id) but never reads the payload.
- **Messages are delivered over any available path.** A direct peer-to-peer channel is preferred; a relay server is the fallback so clients can exchange messages even when they are never online at the same time.
- **The same message id is used on every path.** A client that receives the same message through multiple paths processes it exactly once.

## 1. Terminology

- **User** — a participant identified by a long-lived public key.
- **Client** — a program acting on behalf of one user. A user MAY run multiple clients; this document treats each client as if it holds the user's private key.
- **Peer** — another user a client wants to talk to. "Peer" is a role, not a network concept.
- **Direct channel** — any transport that carries bytes directly between two clients without a relay learning the contents (for example a WebRTC data channel, a LAN link, a Bluetooth link).
- **Relay server** — a server that accepts envelopes from one client and delivers them to another. It does not need to be trusted with message contents.
- **Envelope** — the ciphertext container exchanged on the wire. See §4.
- **Inner message** — the plaintext application message that is encrypted inside an envelope. See §3.
- **Outbox** — a client-local, persistent list of inner messages that still need to be delivered.
- **Receipt** — a small acknowledgement message sent by the recipient to confirm an inner message was received and processed.

## 2. Identity and keys

Each user is identified by a public key on an elliptic curve with a compact public encoding (for example secp256k1 with x-only 32-byte public keys, as used by BIP-340 / Nostr). The corresponding private key stays on the client and MUST NOT leave it.

A user id is the canonical hex or bech32 encoding of this public key. Throughout this spec "user id" and "public key" are interchangeable.

Two users who want to communicate MUST already know each other's public key. How they obtain it (QR code, out-of-band exchange, friend request flow) is out of scope for this document.

## 3. Inner message

Every application-level message a client sends to another user is first built as a plaintext **inner message** object with at least these fields:

| Field          | Type   | Required | Description                                                                                       |
|----------------|--------|----------|---------------------------------------------------------------------------------------------------|
| `id`           | string | yes      | Globally unique message id. MUST be generated by the sender and MUST be stable for retries.      |
| `type`         | string | yes      | Application-specific message type (e.g. `friend_request`, `transaction_created`, `name_changed`). |
| `from_user_id` | string | yes      | Public key of the sender.                                                                        |
| `to_user_id`   | string | yes      | Public key of the intended recipient.                                                            |
| `created_at`   | string | yes      | ISO-8601 timestamp of when the sender created the message.                                       |
| `payload`      | object | yes      | Type-specific fields. Opaque to this spec.                                                        |

Additional fields MAY be present. Implementations MUST preserve unknown fields when storing or forwarding a message.

### 3.1 Message ids

`id` is the unit of deduplication and retry. It MUST:

- Be globally unique with overwhelming probability (e.g. UUIDv4, ULID, a random 128-bit token, or a hash of the message contents).
- Be assigned exactly once by the sender, when the message is first created.
- Remain the same across every retry and across every delivery path. Re-queuing a message from the outbox MUST NOT change its id.

A recipient who has already processed a given `id` from a given `from_user_id` MUST NOT process it again. See §7.

### 3.2 Transport-only messages

Some messages exist only to manage a live direct channel and have no meaning off that channel (for example `ping`, `pong`, and receipts for messages that were just delivered on the same channel). These messages:

- MAY be sent as plaintext inside a live direct channel.
- MUST NOT be sent through the relay server as plaintext.
- If they need to traverse the relay, they MUST be wrapped in an envelope like any other inner message.

Transport-only messages are not persisted in the outbox.

## 4. Envelope

An **envelope** is the object actually transmitted on the wire whenever an inner message has to cross any untrusted boundary (a direct channel carrying data to a second user, or a relay server). It looks like this:

```json
{
  "type": "peer_envelope",
  "envelope_version": 1,
  "id": "<inner.id>",
  "from_user_id": "<inner.from_user_id>",
  "to_user_id": "<inner.to_user_id>",
  "ciphertext": "<base64 of iv || aead(inner_json)>"
}
```

| Field              | Type   | Required | Description                                                                                           |
|--------------------|--------|----------|-------------------------------------------------------------------------------------------------------|
| `type`             | string | yes      | Constant string identifying the envelope type, e.g. `"peer_envelope"`.                                |
| `envelope_version` | number | yes      | Integer version of this envelope format. Bump on incompatible changes.                               |
| `id`               | string | yes      | Copy of `inner.id`. Used for routing, dedup, and acknowledgements without decrypting.                 |
| `from_user_id`     | string | yes      | Copy of `inner.from_user_id`. Needed by the recipient to pick the right key for decryption.           |
| `to_user_id`       | string | yes      | Copy of `inner.to_user_id`. Used by the relay server and by the recipient to verify addressing.      |
| `ciphertext`       | string | yes      | Base64 of the AEAD ciphertext. Contents defined in §5.                                               |

The envelope's plaintext fields are **claims**. A recipient MUST verify those claims against the authenticated inner fields after decryption (see §5.3). A relay server MAY rely on these fields for routing but MUST treat them as untrusted.

Implementations MAY add non-normative fields (e.g. `queued_at` hints from a relay). Unknown fields MUST be ignored by receivers.

## 5. Encryption

### 5.1 Shared secret

For each ordered pair of users `(A, B)`, both sides derive the same shared secret from their own private key and the other user's public key:

```
shared = ECDH(A.private, B.public) = ECDH(B.private, A.public)
```

The shared secret is the x-coordinate of the resulting curve point. If the public key is encoded as x-only, receivers MUST lift it to a full curve point in a canonical way (e.g. choose the even-y point) before the scalar multiplication.

### 5.2 Symmetric key

A symmetric encryption key is derived from the shared secret by a key derivation function. The baseline specified here is:

```
key = SHA-256(shared)   // 32 bytes
```

Implementations MAY substitute any KDF with equivalent or stronger properties (e.g. HKDF with an application-specific info string) as long as both sides agree.

The derived key MUST be treated as sensitive and SHOULD be cached in memory per peer so that repeated scalar multiplication is not required per message.

### 5.3 AEAD encryption

Inner messages are encrypted with an authenticated encryption with associated data (AEAD) construction. The baseline is **AES-256-GCM** with 96-bit IVs.

Encryption:

1. Serialize the inner message to UTF-8 JSON.
2. Generate a fresh 12-byte IV from a cryptographic random source. IVs MUST NOT be reused with the same key.
3. Compute `aead_output = AES_256_GCM_Encrypt(key, iv, plaintext)`. The output includes the authentication tag.
4. Set `ciphertext = base64(iv || aead_output)`.

Decryption:

1. `base64_decode` the ciphertext and split the first 12 bytes as `iv`, the remainder as `aead_output`.
2. Compute `plaintext = AES_256_GCM_Decrypt(key, iv, aead_output)`. If decryption fails, drop the envelope.
3. Parse `plaintext` as JSON into an inner message object.
4. Verify that `inner.id`, `inner.from_user_id`, and `inner.to_user_id` match the envelope's plaintext fields. If any mismatch, drop the envelope.
5. Verify that `inner.to_user_id` is the receiving user's own public key. If not, drop the envelope.

Because the two-party ECDH shared secret is only derivable by the sender and the recipient, successful AEAD decryption proves the envelope was produced by the expected sender. No additional signature is required for sender authentication.

Implementations MAY include the plaintext envelope fields as AEAD **associated data** to bind them to the ciphertext at the cryptographic level instead of relying on the post-decryption cross-check in step 4. Both approaches are conformant as long as a mismatched envelope is dropped.

### 5.4 Algorithm negotiation

`envelope_version` is the single negotiation point for the envelope format and cryptographic suite. A client MUST reject any envelope whose `envelope_version` it does not support. Future versions of this spec MAY introduce new values and new cipher suites.

## 6. Delivery paths

A message can travel from sender to recipient along any of these paths. A client MAY try several paths for the same message; the recipient's deduplication (§7) makes this safe.

### 6.1 Direct channel (preferred)

When the sender's client has an open direct channel to the recipient's client (e.g. a WebRTC data channel), it sends the envelope as a single frame over that channel. The channel carries JSON-encoded envelopes and transport-only messages.

Direct channels are typically negotiated using a signaling relay (§6.3) but may come from any source that lets two clients exchange raw bytes.

### 6.2 Relay server outbox (fallback)

When the sender cannot deliver an envelope directly — because the recipient is offline, or because no direct channel is available — it hands the envelope to a relay server. A relay server MUST implement at minimum these operations:

- `queue_peer_envelope(envelope)` — accept an envelope for later delivery.
- `peer_envelope(envelope)` — push a previously queued envelope to a recipient.

The relay server behaves as follows:

1. On receiving `queue_peer_envelope`:
   1. Validate that the envelope has `id`, `from_user_id`, `to_user_id`, and `ciphertext`.
   2. If the recipient is currently connected, immediately push `peer_envelope` to them. If the push succeeds, the server MAY drop the envelope without storing it.
   3. Otherwise, store the envelope in a per-recipient queue keyed by `envelope.id` (see §6.4 for limits).
2. On receiving a `register` from a client that announces its own user id:
   1. Flush every envelope stored for that user id by pushing `peer_envelope` messages, one per envelope.
   2. After a successful push, remove the envelope from the queue.

The relay server MUST NOT modify envelopes. Clients MUST assume the server might reorder, drop, or duplicate envelopes; dedup and retries live on the clients.

The relay server is an untrusted intermediary. It learns `from`, `to`, and `id` for every message routed through it, plus approximate timing. It does not learn the inner message contents.

### 6.3 Signaling for direct channels

When direct channels are WebRTC-like, the relay server also typically acts as a signaling relay: it announces presence, tells two clients to open a direct channel, and forwards offer/answer/ICE payloads between them. This is orthogonal to the envelope format and is specified separately per transport. The important invariant is that application messages — as opposed to signaling — travel inside envelopes.

### 6.4 Server queue bounds

Relay servers MUST bound their per-recipient queue to avoid unbounded growth. When the queue for a recipient is full:

- The server MAY evict the oldest stored envelope and accept the new one, OR
- The server MAY reject the new envelope.

Either policy is conformant as long as the limit is documented. Clients MUST be prepared for their envelope to be silently dropped and rely on retries (§8.2) rather than any server-side guarantee.

### 6.5 Multiple relay servers

A client MAY be connected to more than one relay server at the same time, and a given envelope MAY be handed to several of them. Recipients rely on message-id deduplication to make this safe. There is no coordination between relay servers.

## 7. Deduplication

Every client maintains a set of **processed message ids** keyed by `(from_user_id, id)`. On every inbound inner message — regardless of which path delivered it — the client MUST:

1. Validate the envelope (see §5.3).
2. If `(from_user_id, id)` is already in the processed set, drop the message and SHOULD still send a receipt (§8.1) so a stuck sender can progress.
3. Otherwise, apply the message to local state and add `(from_user_id, id)` to the processed set.

The processed set MUST persist across client restarts. It MAY be pruned by age or size; a pruning policy is conformant as long as no message id is dropped from the set before any sender could reasonably stop retrying it.

Dedup applies equally to:

- The same envelope arriving via direct channel and via relay.
- The same envelope arriving twice over different relay servers.
- The same envelope arriving twice through a multi-hop peer mesh.
- A sender retrying after a crash.

## 8. Acknowledgements and retries

### 8.1 Receipts

For every inner message a client accepts and processes, it SHOULD send a **receipt** back to the original sender. A receipt is itself an inner message with:

- `type = "received"`
- `from_user_id` = the recipient of the original message (now the receipt sender)
- `to_user_id` = the sender of the original message
- `payload.message_id` = the `id` of the message being acknowledged
- `payload.result` = an application-defined status, at minimum distinguishing "processed" from "ignored"

Receipts are inner messages and MUST follow the same encryption rules. They MAY be delivered via any path:

- If the recipient has a live direct channel to the original sender, receipts MAY be sent as plaintext transport-only messages on that channel (see §3.2).
- Otherwise the receipt MUST be wrapped in an envelope like any other inner message, and MAY be handed to a relay server for offline delivery.

A receipt MUST NOT itself generate a receipt. On receiving an inner message with `type = "received"`, a client processes it and stops — no acknowledgement is sent.

### 8.2 Outbox semantics

The sender keeps every unacknowledged inner message in its persistent outbox until a matching receipt arrives. While an id is in the outbox the sender MAY:

- Retry delivery through any available path, any number of times, with its own backoff policy.
- Hand the same envelope to the relay server again. Re-queuing is idempotent: the relay server keys its queue by `envelope.id`, so a given envelope takes at most one slot.

Once a receipt for `id` arrives, the sender removes the message from its outbox and stops retrying.

If a client has previously handed an envelope to a relay server and then observes that the relay server has restarted (for example, by detecting a new WebSocket session), it MUST be prepared to re-queue the envelope. In practice this means the client SHOULD clear any in-memory "already queued on server" tracking whenever it (re-)registers with a relay server.

### 8.3 Sender-side dedup hint

A client MAY keep a per-session cache of envelope ids it has already handed to the relay server in the current session, to avoid spamming the relay with duplicates of the same envelope while no new events have changed its state. This cache is an optimisation only and MUST be reset on every (re)registration with the relay.

## 9. Data flows

This section walks through the four combinations of sender and recipient online state.

Legend:

- `A → B` means user A sends to user B.
- `[…]` denotes an encrypted envelope.
- `-->` is a direct channel, `==>` is a relay path.

### 9.1 Both online, direct channel available

```
A                          Relay                           B
|   wrap inner as [msg]                                    |
|------------------------- [msg] -------------------------->|
|                                                          |   decrypt, verify, apply
|                                                          |   add id to processed set
|<------------------------ [receipt] ----------------------|
|   or over the same direct channel as plaintext           |
|   remove id from outbox                                  |
```

The relay server is not involved. This is the common fast path.

### 9.2 Both online, no direct channel (yet)

```
A                          Relay                           B
|--- queue_peer_envelope([msg]) --->|                      |
|                                   |-- peer_envelope([msg]) -->|
|                                                          |   decrypt, verify, apply
|                                                          |<-- queue_peer_envelope([receipt]) --|
|<-- peer_envelope([receipt]) ------|                      |
```

The relay forwards the envelope immediately instead of storing it. Same protocol on the receipt path.

### 9.3 Sender online, recipient offline

```
A                          Relay                           B (offline)
|--- queue_peer_envelope([msg]) --->|                      .
|                                   |   store under B      .
|                                   |                      .
                                    .                      B comes online, registers
                                    |-- peer_envelope([msg]) -->|
                                    |                       |   decrypt, verify, apply
                                    |<-- queue_peer_envelope([receipt]) --|
A                                   |                       |
|<-- peer_envelope([receipt]) ------|                       |
|   remove id from outbox                                   |
```

The relay stores the envelope in B's queue until B registers, then flushes it. B sends the receipt back the same way, through the relay if A happens to be offline when B is processing.

### 9.4 Both offline at different times

```
A                          Relay                           B
|--- queue_peer_envelope([msg]) --->|                      .
|   (A goes offline)                |   store under B      .
                                    |                      .
                                    .                      B registers
                                    |-- peer_envelope([msg]) -->|
                                    |                       |   decrypt, verify, apply
                                    |<-- queue_peer_envelope([receipt]) --|
                                    |   store under A      |
                                    |                      |   (B goes offline)
A reconnects                        |                      .
|-- register --------------------->|                       .
|<-- peer_envelope([receipt]) ------|                      .
|   remove id from outbox            |                      .
```

Neither user is ever directly connected to the other. The relay holds both the original message and its receipt until each side comes back. If A retries in the meantime, the relay's per-id queue (§6.2) deduplicates the stored envelopes automatically.

### 9.5 Racing paths

If A has both a direct channel to B and a relay route, A MAY send the envelope on both. B will decrypt whichever arrives first, apply the message, and drop the second as a duplicate (§7). B's receipt may likewise arrive at A via both paths; A processes whichever arrives first and treats the second as a no-op.

## 10. Security properties and non-goals

Properties provided by this protocol:

- **Confidentiality** against relay servers and network observers: envelopes are AEAD-encrypted under a key only the sender and recipient can derive.
- **Integrity** of the inner message: AEAD authentication makes any tampering observable.
- **Sender authentication** between two known users: successful decryption proves the envelope came from the claimed `from_user_id` (given the recipient trusts the public key binding).
- **Replay resistance at the application layer** via the dedup set (§7). The protocol itself does not prevent a relay from replaying an envelope, but replays are discarded by the recipient.

Properties **not** provided:

- **Forward secrecy.** The ECDH key is long-lived. Compromise of either side's private key exposes all past messages that were recorded on the wire.
- **Metadata privacy from the relay.** The relay learns the pair `(from_user_id, to_user_id)` and the `id` for every envelope it sees.
- **Ordering across paths.** Messages from the same sender are not guaranteed to arrive in any particular order. Applications needing ordering MUST carry ordering information inside `payload`.
- **Delivery guarantees.** Clients retry, relays MAY drop, and direct channels come and go. "Delivered" is defined only by the receipt (§8.1).
- **Denial of service protection on the relay.** Rate limiting and quota enforcement are relay-specific policy.

## 11. Versioning

This document describes version `1` of the envelope format. Any incompatible change — new required fields, different crypto suite, different serialization — MUST increment `envelope_version`. Receivers MUST reject unknown versions rather than trying to guess.

Inner message `type` values are application-level and evolve independently; adding a new type is not a protocol change.
